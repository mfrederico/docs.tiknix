Frameworks usually arrive in one of two shapes. Either you install a library and write your app around it, and every upgrade is your problem; or you fork a starter kit, and on the day you start editing it, it stops being upgradable. Neither works when an agent writes most of the code: the agent will happily edit the starter kit, and nobody will notice until the next release cannot be applied.

A Tiknix app is the first shape with a hard line drawn through it. The platform's code — the runtime — is a Composer package the app requires. Everything else at the app's root is the app's own. The line is enforced, not suggested.

Two halves of one app

vendor/tiknix/runtime/{controls,lib,models,services,mcptools,views,…}   the platform — read-only
controls/ lib/ models/ services/ mcptools/ views/ routes/                the app's own code
concepts/ connectors/                                                     installed plugins (read-only too)
conf/ data/ database/ secure/ log/ public/                               config, data, web root

The runtime is what every app runs on: routing, the Bean:: wrapper over RedBeanPHP, members, sign-in and two-factor, the admin pages, connections, pipelines, the MCP server and its tools, plugins, the page shell, and the agent runner that builds tasks. The app is everything it adds: its controllers, models, pages, seeds, and the menu that links them.

Code finds the two halves by asking, never by counting directories: \app\Paths::root() is the app, \app\Paths::runtime() the runtime. The autoloader, the view resolver, seeds, MCP tools and the agents' guidance all look in the app first, which is what makes the rest of this article work.

A new page is a controller of the app's own

The runtime's controllers — Admin, Auth, Member, Settings and the rest — serve URLs the app does not own. A page an app needs, even one a plan names as /admin/customers, is built as controls/Cafe.php serving /cafe/customers, with its permission row seeded and a link from the app's menu. The runtime's pages are reused by linking to them, never by adding a method to them.

Changing what the runtime does

In order of preference:

  1. Extend it. The runtime exposes slots — \app\Chrome::add('prepare', 'app/nav') adds the app's part of the menu; 'footer', 'actions', 'dashboard' and others take parts of the page shell — plus settings, and classes your own code can call. Most changes are one of these.
  2. Override it, only when the runtime's own behaviour must change: 
    php scripts/clitool.php --override=views/admin/index.php
    copies the file to the same path in the app, records it in overrides.lock, and points the autoloader at the copy. Override the smallest thing that works — a view, not its controller.
An overridden file is never upgraded again. When a release changes the runtime's copy, --update names the override STALE, and its owner reconciles it.

Copying a runtime file into the app by hand is refused at the keyboard. It would half-work, which is worse than not working: a hand-copied controller is never loaded (the class map still names the runtime's), while a hand-copied view is — so new methods 404 and the view fails on variables nothing passes it.

Updates are releases

The runtime is released as git tags. An app pins one in its composer.json and moves with: 

php scripts/clitool.php --update

which installs the release, runs the seeds, names any stale override, and regenerates the agents' guidance. Hosted apps are updated by the platform as releases go out; the busy check comes first, so an app in the middle of a build is not updated under it.

The agents' guidance is generated

The rules an agent reads before it touches an app — the file Claude Code reads as CLAUDE.md and other agents as AGENTS.md — are built by clitool --agent-sync from the runtime's agent/guidelines/, plus each enabled plugin's guidelines.md, plus any section the app writes itself in its own agent/guidelines/ (an app file with a runtime section's name replaces it). A runtime release can therefore change what every app's agents know — which is how a lesson learned in one project becomes a rule in all of them.

Plugins

Features that are optional but shared — e-signatures, a CRM, a lead machine — are concepts: plugins installed from a catalog into concepts/<name>/ and recorded in concepts.lock. They are read-only for the same reason the runtime is: an app adapts a plugin through its slots, settings and classes, from its own code, so the plugin can be updated. A plugin never names a provider; it declares a role (mail, payments) and the app binds that role to one of its connections.

Data and code stay apart

What the app writes while it runs lives under data/, database/, secure/, log/ and similar; never under controls/, lib/ or views/. Code changes are commits. Tables and permission rows ship as seeds in services/Schema/Seeds/ (an app's own from number 50 up) — and a seed is for what the app needs, never for one owner's records.

Honest notes
  • An override is a fork of one file. It is the right tool when you need it, and it is debt from the day you take it: every release that touches that file is yours to reconcile.
  • The runtime is still moving fast. Releases are frequent and numbered as pre-releases. Hosted apps take them automatically; a self-hosted app should read what changed before it updates.
  • Slots exist where someone needed them. When the runtime has no slot for what you want to change, the honest options are an override or asking for a slot — not a clever workaround in a view.
