Once more than one agent works on a codebase, you have an organisational problem, not a prompting problem. Who decides the design? Who may change the live app? What happens when two agents edit the same file? Who reviews, and does it mean anything when the reviewer is the model that wrote the code? And when do you stop spending?

Tiknix answers each of these in code rather than in a prompt. This article follows one request — typed in Ask — from plan to live, and names the rule that holds at each step.

Where the work happens

Every project runs in its own container, and the checkout in that container is the running app. There is no staging copy to promote: a task is built on its own git branch, in its own worktree, and merging it is publishing it. That makes the merge the one gate that matters, so everything below is about what a task must prove before it reaches it.

1. The planner owns the design

The planner is the only agent that makes architectural decisions. It reads the app first — through the app's own MCP tools and the project's notebook — and must classify every capability as REUSE, EXTEND or NEW before proposing work. Its plan is a graph of tasks, each carrying:

  • files — what it will touch
  • reuses — which existing primitives it builds on
  • depends_on — which tasks must land first (tasks that touch the same files are chained, so two agents never edit one file at once)
  • verify — the checks that prove it, quoted from the request's "how we will know it worked"
  • effort and risk, each 1 to 5

A task the planner marks complex gets a second pass that investigates and splits it before anything is built; a last pass checks the graph as a whole — no cycles, foundations first, every route with its permission level.

2. Every task is ranked

PlanRank turns the planner's scores into something a person can read at a glance — Minor, Low, Medium, High, Critical — and raises a task's risk on evidence the planner may have missed: it touches sign-in, permissions or who sees what; another task changes the same file. The rank decides how hard a task is checked, which is the point: a typo fix and a change to who may see invoices should not get the same scrutiny.

3. Tasks build side by side, by level

Tasks with nothing between them build at once; a task starts when what it depends on has been merged. How many run at once is a setting on the project's agent (at once, under its Limits) — some providers serve one request at a time, and the setting says so rather than letting the build find out by failing.

Each task gets a sandbox, not a description of one:

  • its own copy of the app's database and config, served by its own PHP server;
  • three people already signed in — a member, an admin, a root — one cookie jar each;
  • the app's tests run before it starts, so what was already failing is not blamed on it;
  • a browser, lent from the platform's QA host, that can open the sandbox's address;
  • no connections: a sandbox cannot send mail or charge a card.

4. Workers implement the spec; they do not redesign it

A task description is a spec, not a suggestion. If a worker finds the spec wrong, it stops and asks — the question reaches its person in Ask and by email — rather than re-deciding the design.

A worker that improvises produces code that is locally reasonable and globally incoherent: three tasks solving the same problem three compatible-looking, incompatible ways. Stopping is cheap; silent divergence is invisible until it breaks. The corollary still holds: a task a model cannot carry out without a judgement call is an under-specified task. Fix the plan, not the worker.

5. Before the merge: what the task must show

When the agent finishes, the platform — not the agent — decides whether its work is merged:

  • every page it changed is requested again as a visitor and as each of the three people; a PHP file left empty or unparsable, or a browser installed in the app, fails it outright;
  • the app's tests run again; what newly fails is written on the task;
  • a task that changed what a person sees, while a browser was lent, is not merged until that browser opened each changed page — the sandbox records who asked for what, so a curl does not count;
  • a runtime file copied over by hand, or a seed in a folder nothing applies, is refused with the fix named.

The work is committed as the member who asked for it, and merged by the orchestrator: one writer to the app's history.

6. Risky tasks are read twice; critical ones are built twice

A task ranked Medium or above gets a second reading: the project's agent, with no write access, reads what the task changed against its checks and answers PASS or names the problems. Problems become one fix task — Fix what the review of #N found — in the same request.

A Critical task with real effort (risk 5, effort 3 or more) is built twice, by two agents at once, the second told to take a different approach where there is one. Both finish; a judge picks one to keep whole — two answers to one question are never merged into each other. What the other attempt is still good for is its tests: they are run against the kept one, and any that fail become a fix task. A race only starts when two attempts fit within what is left of the request's spending limit.

7. The project learns its own costs

Every task records what it took — time, tokens, turns, which model. PlanLearn turns that into medians per effort level and trouble rates per risk level, for this project, and puts them in front of the next planner (how long, and how many tokens, a task of each effort has taken here). Ask shows a request's floor — the least its longest chain of tasks has taken here — and the spending check before a build uses the same record.

8. After the merge

Merged tasks run their seeds in the live app, then the whole request is checked from outside in a browser (see How Work Is Checked). Each task may propose up to six lines for the project's notebook — a decision and its reason, where something non-obvious lives, a mistake and its fix — added after it merges, so the next run does not rediscover them. Tasks never edit the notebook themselves: they run side by side and would collide.

Retries are bounded

A task that fails is retried automatically only for failures a retry can fix — a session that did not start, a page check it can satisfy in its kept copy — at most three times, and never again when the same failure repeats. Infinite retries are how a safety net becomes a cost sink.

Honest notes
  • The second reading uses the same model by default. Review by a different model family catches more of the mistakes a model is prone to; today the reviewer is the project's own agent. It still finds real problems — a pass with no write access, against stated checks, is not the same as writing — but it is not decorrelated review.
  • Races are rare by design. Few tasks are Critical with real effort, and a race doubles that task's cost. Expect a handful a month on a busy project, not one per request.
  • A request's time is mostly between tasks. A task's own checks add seconds; waiting for the level before it, for a free slot, or for a review is where the minutes go.
  • This is supervised, not autonomous. A person sets the goal, answers the questions, and approves the plan. The machinery makes a small team of agents safe to leave running; it does not decide what to build.
