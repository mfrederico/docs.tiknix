A framework's defaults optimise for the first ten minutes: install it, sign in, see something work. Production has different requirements, and the gap between the two is not a flaw. It is a step, and the only real failure is not knowing the step exists.

Most Tiknix apps now run on Tiknix's own hosting, where much of that step is done before the app answers its first request. This checklist says what is already handled there, what is still the owner's, and — for an app run on your own server — the rest.

Already done on Tiknix hosting

  • Its own container. Each app runs alone, with only public/ served; config, database, logs and secure/ are not reachable over HTTP.
  • Production settings. environment = "production" and debug = false, so no stack trace reaches a browser and the session cookie is marked Secure (HttpOnly and SameSite=Lax are always on).
  • No known password. The seeded admin password is refused at sign-in; the first sign-in sets the owner's own, and only the owner's email can complete setup.
  • Secrets in secure/, readable by the app alone, with each app's connections sealed by its own key.
  • Uploads off the disk. Files people upload go to the app's bucket, not to a directory the web server could execute.
  • Runtime updates applied as releases go out, never in the middle of a build.
  • Undo. Each request's build takes a checkpoint of code and data first.

Still the owner's

1. Permission rows, as seeds

Every route needs an authcontrol row, shipped as a seed. Build mode stays on in every app, and what it does is narrow: the first request to a route with no row creates one at admin only (a short list of public pages — the home page, setup — excepted). So a forgotten row locks a page rather than opening it. The rule that follows: seed a route's row before anyone opens it, with PermissionCache::seedRule(), which also corrects an automatic row it finds. 

-- What can an anonymous visitor reach?
SELECT control, method, level FROM authcontrol WHERE level >= 101 ORDER BY control;
-- Rows build mode made, still waiting for a decision
SELECT control, method, level, description FROM authcontrol WHERE description LIKE 'Auto-generated permission for%';

2. Your two-factor policy

[security]
two_factor_enabled = true
two_factor_enforce = true   ; false = optional ("Skip for now")

Two-factor is on for admins by default, and optional. If your app has admins on a public address, enforce it — and write down how someone who loses their phone gets back in (clitool --user=… --reset-2fa) before you do.

3. Your domains

An app answers on its Tiknix address from the start. Your own domain is added on the Deploy page; each domain can be its own site, with its own mail sender and its own files.

4. Your connections

Mail, storage, video, texts and accounting are connections you make under Connections. Until you do, the pages that need them say so. Check each from the live app once — a build task's sandbox never has them.

5. The logs, read

New hosted apps log at DEBUG. Turn it down to INFO once the app is settled — DEBUG in production is a disk and a privacy cost. Errors on the live app reach the Builder as problems Tiknix found; the rest of the log is yours to read.

6. Data you cannot lose

Checkpoints are for undoing a build, not a backup strategy. If the app holds data that cannot be recreated, keep copies you control, off the machine — and restore one somewhere at least once. An untested backup is a belief.

On your own server, also

  • Only public/ is the web root. Request /conf/config.ini and /database/ and confirm both 404.
  • Set environment = "production" and debug = false. The Secure cookie flag follows the first.
  • Protect conf/ and secure/. Out of version control, not readable by other users, backed up where you can find them. Losing secure/connections.key means every connection must be made again.
  • Prefer 775 with the right group to 777. World-writable directories are a local privilege-escalation gift.
  • Rate-limit at the edge. The built-in limiter is session-based; it does not stop a distributed attempt where every client starts fresh.
  • Lock down development surfaces — the Demo controller and anything like it — with explicit ROOT rows, or remove them.
  • Deploy from git and keep the checkout clean, so git status tells you the truth. A hand-edited file on the server is an incident to reconcile.

Two switches that are no longer advice

Earlier versions of this checklist said to do these. Do not:

  • Turning build mode off. With it off, a route without a row is public. With it on, such a route becomes admin-only on first use. On is the safer state.
  • Freezing the schema. Some tables are still created on first use, and a frozen database turns that into a live error. Instead, every automatic schema change is written to the log with the line that caused it. Freezing is available per environment (DB_FREEZE=true) for an app whose every table has a seed.
Honest notes
  • This is not a security audit. It is the framework-specific set. On your own server, TLS, OS patching, SSH and firewall rules are still yours.
  • The permission table is still the highest-value check. Build mode makes a forgotten row fail closed, but a row seeded at the wrong level is still wrong. Read the anonymous-access query after every request that adds routes.
  • Some hardening costs usability. Enforced 2FA brings support load; short sessions annoy people. Make those trade-offs on purpose.
  • Do this before launch. Every item is minutes on an unlaunched app and a scramble on a live one.
