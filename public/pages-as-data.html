Pages as Data

A page says what is on it — its title, its one action, its rows and fields — and Ui decides how it looks, so every page of an app reads the same way.

Ask an AI agent for an admin page and you will get one. It will have a card, a table, a form, three buttons in a row and a success message in green — and the next page it writes will have a slightly different card, a table that scrolls sideways on a phone, and four buttons. Each page is fine. The app is not: nothing reads the same way twice, and the person using it has to work out each screen from scratch.

Tiknix's answer is to take layout away from the page. A page of the app's own says what is on it — its title, the one thing to do there, the rows, the fields — as data, and \app\Ui decides how that looks: spacing, hierarchy, where actions sit, how a list reads on a phone, how a delete is confirmed.

What a page says

<?= \app\Ui::page(['title' => 'Customers', 'lead' => 'Everyone who has ordered.',
                   'primary' => ['label' => 'Add a customer', 'url' => '/cafe/customer', 'icon' => 'plus-lg']]) ?>
<?= \app\Ui::table(['rows' => $rows, 'count' => 'customer',
    'columns' => [['label' => 'Customer', 'value' => 'name', 'sub' => 'email', 'url' => fn($r) => '/cafe/customer?id=' . $r->id],
                  ['label' => 'Status', 'value' => 'status', 'as' => 'badge', 'tones' => ['active' => 'success']],
                  ['label' => 'Since', 'value' => 'created_at', 'as' => 'date', 'quiet' => true]],
    'actions' => fn($r) => [['label' => 'Delete', 'post' => '/cafe/delete', 'fields' => ['id' => $r->id],
                             'confirm' => "Delete {$r->name}? Their orders stay.", 'danger' => true]],
    'empty' => ['title' => 'No customers yet', 'text' => 'They appear here after their first order.',
                'action' => ['label' => 'Add a customer', 'url' => '/cafe/customer']]]) ?>

There is no <div class="container">, no card, no hand-written table and no confirm(). The same few calls cover most of an app: Ui::page, Ui::table, Ui::form, Ui::agenda (things that happen at a time), Ui::detail (one record's facts) and Ui::notice.

The rules it holds you to

Each is about what a person has to read and decide, not about taste:

  • One primary action per page, named as a verb with its object — "Add a customer", never "Submit" or "New". Others go in a quieter menu.
  • A list shows what tells rows apart — at most seven columns. The first names the row and links to it; a second fact goes under it; columns a phone can drop are marked quiet.
  • Things that happen at a time are an agenda, not a table — grouped by day, Today and Tomorrow in words, soonest first. A date column makes the reader do the grouping.
  • Every list has an empty state that says what belongs there and how to add the first one.
  • A form asks only what it needs now. More than eight fields in one run is refused: group them in sections, or fold the rarely-needed ones under "More options". Two to four choices are radio buttons, not a dropdown.
  • Words are the user's, not the schema's — "Stop showing it at", not expires_at.
  • Something destructive is a POST with a confirmation that says what will be lost.

A spec that breaks a rule is refused with the fix in the message — an unknown key, a form with ten loose fields, a table with no empty state. That is deliberate: a page that renders wrong quietly is worse than one that refuses loudly, because the loud one gets fixed in the task that wrote it.

Which pages, before any view

The harder decision is not how a page looks but which pages a feature needs. The ui_pattern MCP tool answers it from the shape of the data: given a bean (or the columns of one not built yet), it says whether this is a list and a form, a page per record, an agenda by day, a conversation, a single settings form, or a list on its parent's page — which columns tell rows apart, what the form asks up front and what folds away, and the Ui code to start from. The planner calls it before it plans a page.

Hand-made pages still exist

A calendar, a chat, a dashboard or a public landing page is not a list, a form or a record, and is written by hand — on the design system's classes and Bootstrap 5.3 (see Bootstrap as a Design Primitive), still opening with Ui::page(). It says so in one line, // ui: hand-made — a calendar, and the page check stops asking it to be a table.

The check, and the order of work

full_validation reports what a view does by hand that Ui decides — a hand-written table or form, two primary buttons, its own flash output, a hard-coded colour, no heading — as warnings on the task that wrote it.

And it fixes the order of work. A feature's first task is its data, rules and routes, with pages built from Ui: correct and usable, and done. How it feels — the order of things, the wording, what is folded away — is its own design task, after the data works, made by looking at the pages in a browser at phone and desktop width.

Honest notes
  • Refusals are 500s. A spec Ui refuses throws, and in a live page that is an error page until the view is fixed. The page check after every task exists so a refusal is caught in the sandbox, not by a visitor.
  • It is opinionated on purpose. Seven columns, eight loose fields, one primary button: some pages will want one more. The rule is the default an agent cannot argue its way past, not a law of nature — sections, folded fields and a page per record are the ways through.
  • Every app looks related. That is the point for the people using it, and a cost for an owner who wants their app to look unlike the others. The palette, type and logo are still theirs.
