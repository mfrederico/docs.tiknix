How Work Is Checked

Six layers, each catching what the last cannot — from a blocked edit to a browser that signs in as every kind of user — and how what they find becomes a rule.

Generating code stopped being the hard part some time ago. Knowing whether it works is the hard part, and it is where AI-built software usually fails: a change that reads plausibly, compiles, and breaks a page nobody opened. Plausible but unverified code is not a gift; it is a debugging session you have not started yet.

So Tiknix spends most of its machinery on checking, in layers. Each layer catches what the one before it cannot, and each is evidence the platform gathers itself — never a claim an agent makes about its own work.

Layer 1: before a file is written

Every write an agent makes passes through an edit hook that blocks what is never right in a Tiknix app: an edit under the read-only runtime, a runtime file copied over by hand, raw R:: calls the Bean:: wrapper covers, a value interpolated into SQL (an IN list built with Bean::genSlots() is fine), a flash message no page shows. The block says what to do instead. Cheap mistakes are stopped at the keyboard, where they cost nothing.

Layer 2: inside the task

A task works in a sandbox — its own copy of the app's data, its own server, three people already signed in — so it can check what it built instead of guessing. Before it may finish:

  • The page check asks for every page it changed, as a visitor and as each of the three people, and names any that answer 500 with the log line that says why.
  • The app's tests run before and after. What already failed is not the task's; what newly fails is written on it.
  • The lent browser. Every build borrows a real browser from the platform's QA host. A task that changes what a person sees is not merged until that browser has opened each changed page — the sandbox records which address asked for which page, so this is proof, not a promise. If the browser could not be used, the task must say why.
  • full_validation warns about what a page does by hand that Ui decides (see Pages as Data) and about a page nothing links to — a feature nobody can reach by clicking is not done.

Layer 3: a second reading

A task ranked Medium risk or above is read again, read-only, against the checks it promised; a Critical one is built twice and the other attempt's tests are run against the one kept (see How a Request Is Built). What either finds becomes a fix task in the same request.

Layer 4: the check after the build

When a request's tasks are merged, the app is checked from outside, as it now runs. An agent with a browser signs in as each kind of user — root, admin, member — exercises what the request changed, and takes a screenshot of each changed page at desktop (1280×800) and phone (390×844) width. The screenshots appear under the request in Ask, each beside the check it proves, and are emailed to the owner with the verdict.

What it finds is not left as a report:

  • each failure becomes a problem Tiknix found, shown in Ask with its screenshots and a Fix it button;
  • on every project, it also starts its own fix, which is checked again when it lands — at most two rounds, then it waits for a person;
  • the failure is written into the project's notebook as a lesson, so the next build looks for it before calling its own work done.

The share of requests that pass this check the first time, without a fix, is the number that says whether building is getting better. Tiknix's Insights page shows it to the platform's admins, per project and overall (on 16 October 2026: 88 of 134 requests over the previous 30 days, 66%).

Layer 5: the tests you keep

QA Testing holds tests described once and run from outside the app: web pages driven in a browser, APIs, MCP servers. They run when you ask, on a schedule (every five minutes to once a day), and — after every build is checked — all of a project's active tests run once more, because what was just built should not break what was already working. You hear when a suite turns red, and again when it is green; not on every run. A run uses no model, so it costs no tokens.

Layer 6: what was learned, kept

A check that only fixes this build has done half its job. The rest is making the next build not need it:

  1. Agents write down what tripped them, as notebook lessons, project by project.
  2. Lessons about the platform — true in any project — are offered to Tiknix's knowledge base, where a person publishes them. A project's agent asks the knowledge base before it asks its user about support.
  3. The same lesson written down again is counted, not discarded. A lesson that has come up three times is a mistake agents keep making, and the knowledge desk says it should become a rule in the agents' guidelines — which every agent reads before it starts, rather than only one that thinks to ask. If it keeps coming up after that, the rule is not working, and the desk says so.
Honest notes
  • A sandbox cannot reach connected services. Pages that send mail, store a photo or call QuickBooks are checked for their "not connected" behaviour inside a task; only the check after the build sees them work for real.
  • The check after the build looks at what the request changed. It is not a regression suite for the whole app. That is what QA Testing's kept tests are for — and they only exist once someone writes them.
  • Automatic fixes spend tokens without asking. They are capped at two rounds and stay within each agent's spending limit, and they can be switched off per project; but on, they do run unattended.
  • The first-time pass rate is honest, not flattering. It counts every request the check looked at, including ones whose failure was the check's own browser. Read it as a trend.
