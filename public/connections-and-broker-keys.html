Third-Party Credentials Without Sprawl

Each app's tokens kept in that app and sealed with its own key, connectors behind one interface, and revocable broker keys instead of shared secrets.

The moment your application talks to somebody else's — Stripe, Shopify, QuickBooks, an email provider, a storage bucket — you have acquired a credential problem. Someone's token now lives in your system. It has to be stored, scoped to the right customer, used from the right place, and revoked when things go wrong. The path of least resistance is an environment variable and a comment saying "TODO: encrypt this."

Tiknix takes a more structured route. The shape is worth understanding even if you never use its connectors, because it generalises to any integration you build: credentials belong to the app that uses them, sealed with that app's own key, and anything that must stay with the platform is reached through a revocable capability rather than a shared secret.

Credentials live in the app that uses them

Each app keeps its connections in its own data/connections.db, sealed with a key that belongs to that app alone — secure/connections.key, outside the web root and outside git. The platform's own database holds none of a customer's tokens. Two consequences follow:

  • One customer's token cannot be reached from another customer's app. They are in different containers, sealed with different keys.
  • Credentials never enter git history. An app's main database is committed with its checkpoints so a request can be undone; the connections store and its key are not, by construction rather than by an ignore rule someone might forget.

A value that will not decrypt is treated as a fault, never as "not set". Those two states must not produce the same answer: one is an empty row, the other is a broken key, and only the second is an incident.

Encrypted at rest, with a real cipher

EncryptionService uses libsodium's authenticated symmetric encryption:

$nonce      = random_bytes(SODIUM_CRYPTO_SECRETBOX_NONCEBYTES);  // 24 bytes, per value
$ciphertext = sodium_crypto_secretbox($plaintext, $nonce, $key);
$encrypted  = base64_encode($nonce . $ciphertext);
sodium_memzero($key);                                          // wipe the key from memory when done
  • Authenticated encryption. secretbox is XSalsa20-Poly1305 — tampering makes decryption fail rather than silently produce garbage.
  • A fresh random nonce per value, prepended to the ciphertext, so nonce reuse is structurally impossible.
  • sodium_memzero() after use, so the key does not linger in process memory waiting to appear in a core dump.

Connectors behind one interface

services/connectors/ holds the connector classes behind one interface — Stripe, Shopify, QuickBooks, S3 storage, Bunny Stream, Quo, Instagram, Microsoft, Monday, Telegram, a database, a plain REST endpoint — and a connector can also be data: a JSON manifest describing its endpoint, auth (including OAuth) and calls, interpreted by one class. A provider is prototyped as a manifest and promoted to code when it needs to be; code wins a name collision. Adding a provider is a file, not a change to the OAuth flow.

The OAuth flow runs where the provider's app lives. For a provider where each customer creates their own app (Shopify's custom distribution), the callback is on the customer's project — its own domain, registered in their own app — and the app's credentials are stored on the connection, because a project with two stores needs two apps. For a provider where one platform app serves everyone (QuickBooks), the sign-in happens on the platform, which pushes the connection into the project. Either way the token ends in the project's store. The OAuth state is signed and checked centrally — an unsigned state is how an attacker's account gets attached to a victim's session.

Roles, not providers

Code that needs a service asks for a role, not a provider: Mailer asks for the app's mail connection, Storage for its storage, a plugin for whatever it declares (payments: [stripe]). The app binds each role to one of its connections, per site. Two connections that could fill one role are an error naming the page to fix it, never a guess. See Connected Services.

The broker key: a capability, not a secret

Some things should stay with the platform: Intuit's app secret, the GitHub token that exports code, a member's own model key, the knowledge base. A project reaches them with its broker key, and the platform makes the call on its behalf. The key is built to be survivable when it leaks:

  • it is scoped to one project, and the platform resolves the project from the key — never from what the request says it is;
  • only its SHA-256 hash is stored, so a database dump yields no working key;
  • it is shown once, at creation, and killed by one flag;
  • what it can reach is narrow and rate-limited — renewing that project's own QuickBooks access (20 an hour), publishing that project, asking the knowledge base.

Compare the blast radius. Leak Intuit's app secret and every customer's books are reachable. Leak a broker key and an attacker can renew one project's access, rate-limited and audited, until someone flips a flag. The goal is not preventing every leak; it is making leaks survivable.

The pattern, extracted

  1. Keep a credential with what uses it, sealed with that thing's own key.
  2. Encrypt with an authenticated cipher and a per-value nonce.
  3. Hold what must be central centrally, and hand out scoped, revocable capabilities to it instead of the secret.
  4. Store capability hashes, and show a raw one exactly once.
  5. Treat "will not decrypt" as a fault, never as "absent".
  6. Ask for roles, not providers, and make ambiguity an error.
Honest notes
  • The app's key is a single point of failure for that app. Lose secure/connections.key and its connections must be made again; leak it with the store and its tokens are exposed. It deserves the handling of a production database password.
  • The broker adds a hop. A call through the platform is slower, and the platform's availability now matters for it. For renewals and exports that is worth it; it is not free.
  • Encryption at rest is not encryption in use. A decrypted token exists in memory while a request runs. That is unavoidable; it is worth knowing.
  • Audit logs only help if someone reads them. "Rate-limited and audited" is a real mitigation on paper and inert in practice unless something alerts on anomalies.
